# Membership and Fraternal Ontologies

[![DOI](https://zenodo.org/badge/DOI/10.5281/zenodo.23080656.svg)](https://doi.org/10.5281/zenodo.23080656)

Two layered OWL 2 DL + SKOS ontologies for describing membership organisations of every kind, closed or open, as Linked Open Data:

| Ontology | IRI | Prefixes | Covers |
|---|---|---|---|
| **Membership Organisations** | `https://w3id.org/membership#` · codelists `https://w3id.org/membership/code/` | `mbr:` · `mbrc:` | any membership organisation, closed or open: gentlemen's and ladies' clubs, dining clubs, societies, student nations, hobby and supporters' clubs, associations, political parties, trade unions. Membership lifecycle, admission and fees, offices and terms, gatherings and participation, distinctions and conferrals, reciprocity. Also catalogue facts: founding and closure, status, ownership model, premises with address, coordinates and moves over time, contact details, member counts |
| **Fraternal Orders and Sororities** | `https://w3id.org/fraternal#` · codelists `https://w3id.org/fraternal/code/` | `fraternal:` · `fraternalc:` | extends the membership ontology for orders: degree systems, initiation, lodges and grand bodies, ceremonies, insignia, recognition and amity. Also orders of chivalry, genuine and self-styled, as organisations, with legitimacy recorded as dated assessments by named agents |

"Fraternal" follows the established catalogue term *fraternal organization* (Wikidata, Getty AAT, Library of Congress). It covers women's, mixed and adoptive orders as well as men's.

Status: version 1.1.0 of both ontologies, served from GitHub Pages at <https://society-ontologies.github.io/membership-fraternal/>. The w3id.org IRIs resolve: they were registered in [perma-id/w3id.org#6779](https://github.com/perma-id/w3id.org/pull/6779), and the redirect rules are in [`ids/`](ids/). Every release stays available at its version IRI (for example `https://w3id.org/membership/1.0.0`), served from a frozen copy in [`versions/`](versions/).

```
external/external-declarations.ttl      FOAF, W3C ORG, schema.org, SKOS, PROV terms declared DL-safe
        ▲ owl:imports
membership/membership-ontology.ttl ◄── membership/membership-codes.ttl
        ▲                                        ▲
fraternal/fraternal-ontology.ttl   ◄── fraternal/fraternal-codes.ttl

                your organisation's own ontology (imports fraternal/code or membership/code)

side-car, not imported:  mappings/*.sssom.tsv → mappings/generated/*.ttl
```

## Design rules

1. **Qualified relations.** Anything with a time span or a role is a node: `mbr:Membership`, `mbr:Tenure`, `mbr:Conferral`, `mbr:Participation`. A person's path from prospect to full member is a status on *one* membership, not a change of the person's class.
2. **Class or concept.** Use an OWL class only when the thing has its own properties or constraints. A "value from a list" is a SKOS concept: organisation types, statuses, offices, gathering types, degrees, distinctions. Named classes such as `mbr:GentlemensClub` or `fraternal:Sorority` are *defined* from those values, so a reasoner classifies them and nobody asserts them.
3. **Hub-and-spoke codelists.** An organisation's own list maps to the membership/fraternal hubs, never pairwise to other organisations. Two clubs' treasurers are equivalent because both `skos:exactMatch mbrc:treasurer`. SHACL enforces it: a codelist property takes a concept in its hub scheme, or a local concept with `skos:exactMatch`, `skos:closeMatch` or `skos:broadMatch` to one (not `relatedMatch`, not `narrowMatch`; none of them is `owl:sameAs`). A mapping does not classify an organisation as `mbr:GentlemensClub`: that class needs `org:classification` to be the hub concept itself. **The hubs stay neutral.** A hub scheme holds only what orders in many countries have in common. What belongs to one tradition (the Masonic lodge, the French compagnonnage, the German Studentenverbindung) is in a scheme of its own with `dcterms:isPartOf <hub scheme>`, and its concepts are in that scheme only. Where the hub has a counterpart the concept is mapped to it, as above; where it has none (the German fencing principles, the names of the rites) the concept stands without one, and SHACL accepts a value from a scheme that is part of the hub scheme. A new country or tradition adds a scheme and, where there is a counterpart, mappings; it does not add to a hub scheme. `make skos` checks that a scheme in the fraternal codelists is a hub scheme, a degree system, or a tradition scheme that says which hub it is part of.
4. **Reuse IRIs for things you don't own.** Refer to universities, regiments or historical persons by their Wikidata IRIs. A codelist entry that stands for a real thing can point to it with `foaf:focus`.
5. **Validation in SHACL.** OWL domains would *infer* that anyone who receives a distinction is a member. SHACL *checks* instead, so guests and partners can receive distinctions without becoming members.
6. **Dates** accept `xsd:date`, `xsd:gYearMonth` or `xsd:gYear`, enforced in SHACL, since registers often record only a year. OWL ranges are left open because these types are not in the OWL 2 datatype map. A partial date means a span (`2000` is 2000-01-01 to 2000-12-31), and an end is reported as before its start only when it certainly is: its latest day is before the start's earliest day. Years 0001-9999 with four digits are supported, and a timezone is ignored. Other dates are not ordered and give a warning, never a silent pass.
7. **Several categories.** A membership may have several `mbr:membershipCategory` values (life and founding, junior and overseas); the categories are combinable properties in seven sub-schemes, not an exhaustive division. `mbr:resultingCategory` on an event gives the whole set after the event, not an addition.
8. **Membership numbers** are `xsd:string`, unique per organisation. A number may be reused by a later membership only when the periods certainly do not overlap; without dates, a shared number is reported.

## Using it for your own organisation

1. Write an ontology that imports `https://w3id.org/fraternal/code` (for an order) or `https://w3id.org/membership/code` (for a club or society).
2. Describe the organisation as a `fraternal:FraternalOrder` or `mbr:MembershipOrganization`, classified with `org:classification`.
3. Put its own offices, degrees and distinctions in SKOS schemes. Type them `mbr:Office`, `fraternal:Degree` (in a `fraternal:DegreeSystem`) or `mbr:Distinction`.
4. Keep only what is truly specific to you in your own namespace. If you need names such as "Brother", define them as classes from membership status rather than asserting them.
5. Map your codelists to the hubs in your own SSSOM file, and generate Turtle with `mappings/sssom2ttl.py`.
6. Validate your data with `membership-shapes.ttl`, `fraternal-shapes.ttl` and your own additional shapes. Merge your generated mappings into the data graph, as `make shacl` does: a local codelist value is accepted only when a mapping places it in the hub scheme.

## Describing clubs and associations as catalogue entries

A directory or inventory of clubs or associations needs no extra ontology. Each one is a `mbr:MembershipOrganization`, and a typical directory record maps like this:

| Directory field | Where it goes |
|---|---|
| Name, former names | `rdfs:label`; former names as `skos:altLabel`, or a renaming as an `org:ChangeEvent` |
| Type of organisation | `org:classification`, a value from `mbrc:OrganizationTypes` (gentlemen's, ladies', political, university, professional, arts, armed forces, yacht, service, hobby, supporters' club; political party, trade union …), or from your own list mapped to it |
| Legal form | `rov:orgType` ([W3C Registered Organization Vocabulary](https://www.w3.org/TR/vocab-regorg/)), a value from `mbrc:LegalForms`: unincorporated, incorporated association (registered or not), foundation, company, public-law body. Map a national list such as ISO 20275 to these values with SKOS mappings. Note that `rov:orgType` is declared a sub-property of `org:classification`: a reasoner will also read a legal form as a classification. The shapes run on the asserted data without entailment, so they keep the two apart. |
| Register number | `rov:registration` → `adms:Identifier` (`skos:notation` for the number, `adms:schemaAgency` for the register) |
| How members are admitted | `mbr:admissionMode`: by invitation, proposal and ballot, open application (the board decides), open enrolment (anyone may join), hereditary, ex officio |
| Membership fees | `mbr:membershipFee` → `mbr:MembershipFee` (`mbr:feeType`: entrance, annual, monthly or life-membership fee; `schema:price`; ISO 4217 currency in `schema:priceCurrency`; `mbr:appliesToCategory` when the fee is for, say, junior members only; start and end dates). A fee change is a new fee, and the old one gets an end date. |
| Founded / closed | `mbr:foundingDate` / `mbr:dissolutionDate` (a year is enough) |
| Status | `mbr:organizationStatus`: active, dormant, merged or closed |
| Members' or proprietary club | `mbr:ownershipModel` |
| Men only, women only, mixed | `mbr:genderPolicy`: the registered current picture |
| A change of gender policy, admission mode, ownership model, status, organisation type or legal form | an `mbr:OrganizationPeriod` linked with `mbr:hasPeriod`, carrying the value (`mbr:genderPolicy`, `mbr:admissionMode`, `mbr:ownershipModel`, `mbr:organizationStatus`, and `mbr:organizationType` and `mbr:legalForm` in place of `org:classification` and `rov:orgType`, whose domain is `org:Organization`), `mbr:startDate` and `mbr:endDate` for when it applied and `mbr:decisionDate` for when it was decided (a members' vote may be taken one year and take effect the next). One period per change, with only the properties it concerns. The current value is not derived from the periods. A change of policy does not change `org:classification`. |
| Address | `org:hasSite` → `mbr:Premises` → `schema:address` → `schema:PostalAddress` (`schema:streetAddress`, `schema:postalCode`, `schema:addressLocality`, ISO country code in `schema:addressCountry`) |
| City as a linked place | `schema:containedInPlace` on the premises, with the city's Wikidata IRI |
| Map position | `schema:geo` → `schema:GeoCoordinates` (`schema:latitude`, `schema:longitude`) |
| Moves between clubhouses | one `mbr:Occupancy` per period (`mbr:occupant`, `mbr:occupiedPremises`, start and end dates) |
| Same building, new address (street renamed or renumbered) | several `schema:address` values on the premises, each with its own `mbr:startDate`/`mbr:endDate`. The current address is the one without an end date, and only one is allowed. |
| Mergers | an `org:ChangeEvent` with `org:originalOrganization` and `org:resultingOrganization` |
| Website, e-mail, telephone | `schema:url`, `schema:email`, `schema:telephone` |
| Secretary, chairman … | an `mbr:Tenure` with `org:role` (for example `mbrc:secretary`) and a start date. The current holder is the tenure without an end date. |
| Membership size | `mbr:hasMemberCount` → `mbr:MemberCount` (`mbr:count`, `mbr:asOf`) |
| House dress code | `mbr:dressCode` on the club |
| Reciprocal clubs | `mbr:reciprocalWith`; `mbr:ReciprocityAgreement` for dates and terms |
| Wikidata item | an `owl:sameAs` linkset, or `schema:sameAs` for a looser link |

Complete fictional examples are in `tests/data/klubb-exempel.ttl` (private clubs) and `tests/data/forening-exempel.ttl` (open-membership organisations). `tests/data/organisationsperioder-exempel.ttl` shows a change of gender policy and of ownership. `tests/cq/09` and `tests/cq/10` show the inventory and history queries, `tests/cq/11` the fees in force in a given year and `tests/cq/12` the organisations that had a given gender policy in a given year.

Office-holders of existing clubs are living people, so their names are personal data. A public inventory can record the office with the name left out, or give names only where the club already publishes them. Who belongs to a political party, a trade union or an organisation with a religious or philosophical aim is *special-category* data under GDPR Article 9; see the scope note on `mbr:Membership`.

## Degrees and orders of chivalry

- **Degree rank is positional.** `fraternal:degreeRank` gives a degree's place in the numbered sequence (1 = entry). The order's own numeral or abbreviation, which may differ or even run in reverse, goes in `skos:notation`.
- **Degrees outside the sequence** (honorary, office, side, associate and emeritus degrees) have no rank. They carry a `fraternal:degreeKind` from `fraternalc:DegreeKinds` instead; SHACL requires one or the other.
- **Three kinds of "order" with knightly grades** are kept apart, because what separates them is a claim:

| Kind | Classification | What it is |
|---|---|---|
| Order society in the chivalric style | `fraternalc:chivalricStyleOrder` | uses grade names such as knight and commander internally and makes no claim to be an order of chivalry |
| Order of chivalry | `fraternalc:orderOfChivalry` | has a generally recognised fons honorum (a state, a reigning or formerly reigning royal house, the Holy See) |
| Self-styled order of chivalry | `fraternalc:selfStyledOrderOfChivalry` | claims to be an order of chivalry without a recognised fons honorum |

Whether an order is genuine is a judgement. Record it as a `fraternal:LegitimacyAssessment`: the assessed order, who assessed it (a commission, a state, the Holy See), the outcome, the date and the source. Never assert it on your own authority. An order of merit that consists only of a dignity and its insignia, with no body of members, is a `mbr:Distinction`, not an organisation. See `tests/data/riddarorden-exempel.ttl`.

## Linking between ontologies ("sameAs")

| Linking… | Use | Never |
|---|---|---|
| the same real-world individual under two IRIs | `owl:sameAs`, **only** in separate linkset files | between a concept and a thing, or old/new IRIs |
| an individual to a page that only *indicates* identity | `schema:sameAs` (no OWL merge semantics) | |
| class → class across layers | `rdfs:subClassOf`; `owl:equivalentClass` only if truly equivalent both ways | `owl:sameAs` |
| property → property | `rdfs:subPropertyOf` / `owl:equivalentProperty` | |
| a class/property → Wikidata item/property | `skos:exact/close/broad/narrow/relatedMatch`, declared as annotations | `owl:equivalentClass` (Wikidata items are not OWL classes) |
| concept → concept (organisation ↔ hub ↔ Wikidata/AAT) | `skos:exactMatch` (transitive, so only when confident), `closeMatch`, `broad/narrowMatch`, `relatedMatch` | `owl:sameAs` |
| concept → the thing it names | `foaf:focus` | |
| old IRI → new IRI | `dcterms:isReplacedBy` + `owl:deprecated` | `owl:sameAs` |

Relations between organisations: `mbr:reciprocalWith`, `fraternal:recognizes`, `fraternal:inAmityWith`, `fraternal:hasJurisdictionOver`, `fraternal:warrantedBy`, `fraternal:modelledOn`, `fraternal:namedAfter`, `fraternal:fonsHonorum`, `fraternal:LegitimacyAssessment`, `org:subOrganizationOf`, `org:ChangeEvent` + `org:resultedFrom`.

To add or change a link, edit the `.sssom.tsv` file (`mapping_justification` is required) and run `make mappings`. The ontologies never import mappings: consumers load them as a separate graph, so a wrong link can't silently merge data. Cross-publisher `owl:sameAs` between *persons* belongs only in private linksets, because membership of an order can be sensitive personal data under GDPR.

## Running the checks

Requires Apache Jena (`riot`, `shacl`, `sparql`) and python3. `dl` and `reason` also need ROBOT, and `reuse` needs pipx.

```
make validate        # Turtle syntax of every file
make shacl           # valid samples produce no SHACL results at all
make shacl-invalid   # each fixture in tests/data/invalid/ produces the violation named by its # MESSAGE: line
make skos            # SKOS quality checks (tests/skos-checks/, must return no rows)
make cq              # competency questions (tests/cq/): each result must equal tests/cq/expected/
make mappings        # SSSOM TSV → mappings/generated/*.ttl
make wikidata-check  # every wd: link exists and is not a redirect (network)
make dl              # OWL 2 DL profile (ROBOT)
make reason          # HermiT: consistency + expected/forbidden inferences + a canary that must be inconsistent (ROBOT)
make reuse           # every file has a license (REUSE)
make i18n            # translations: registered, well-formed language tags and English text behind each (tests/i18n/)
make docs            # regenerate docs/ with pyLODE (pinned to 3.2.1), one page per language, and check that every term's anchor is its IRI's local name; commit the result
```

`mappings/sssom2ttl.py` stands in for sssom-py's `sssom convert`. Either can produce `mappings/generated/`.
